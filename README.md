## Clinical documents & prescriptions

Practitioner-issued **medical letters** and **prescription orders**, signed per document, verifiable by QR code.
Design reasoning, test evidence and open compliance items are in `CANNAPLUG.md` ("Clinical Document & Prescription System").

> **Not a compliance claim.** The technical controls below make a compliant process *possible*. Whether the
> signature method, wording, retention periods and workflow satisfy South African law (HPCSA, Medicines and
> Related Substances Act, ECTA, POPIA) must be confirmed by the practitioner, a pharmacist, a compliance advisor
> and legal counsel. The system refuses to issue anything until an administrator has recorded those decisions.

### Principles (enforced in the database, not the UI)

- **Two document types, two rule sets.** `MEDICAL_LETTER` is never a prescription. `PRESCRIPTION_ORDER` needs a practitioner who is *verified* and separately *authorised to prescribe*, a future expiry date, every prescription field typed by the practitioner, and an ADVANCED-or-better signature. A prescription can never be signed with a simple electronic signature (`CHECK` + policy).
- **Only the practitioner creates, approves and signs.** Administrators, managers, budtenders, automation and AI cannot create or sign (`_require_doctor`). The software never selects or suggests dosage, strength, quantity, route, frequency, duration, repeats, indication or any clinical wording; it only checks presence and format (e.g. quantity in words agrees with figures).
- **Templates are wording, not signatures.** They are versioned (an active version is immutable; a change is a new draft version) and approved by a verified practitioner. The member document is generated *from the template and the practitioner's own entries*, frozen, hashed, shown to the practitioner exactly as rendered, and only then approved and signed. A signature is never copied from a template or reused.
- **Immutability.** A document's text is stored with its SHA-256 (`CHECK` that the hash equals the text). After approval nothing but status, revocation fields and write-once issue fields can change; signed/issued PDFs are never edited. Corrections are a new document version (`supersedes_document_id`). Triggers make this hold even against a buggy service-role caller. Nothing is ever deleted.
- **Least privilege.** No client role can write any clinical table. `authenticated` can `SELECT` only non-clinical metadata columns, and only the rows RLS allows. Clinical content (snapshot, rendered text, storage path, verification token) is read only through audited server functions. Admins configure the system and can *revoke*; they cannot read clinical content or sign.

### Workflow

```
Practitioner (/doctor)                                   System
─────────────────────────────────────────────────────────────────────────────────────────
create draft (assigned, ID-verified member; ACTIVE template)      DRAFT      CREATED, TEMPLATE_SELECTED, DATA_CAPTURED
type every clinical value; "Prepare for review"          ─►  prepare (re-read identity, validate) → render → freeze + SHA-256
                                                                   PENDING_DOCTOR_REVIEW
open the document: sees the EXACT text + hash                      DOCTOR_REVIEW_STARTED, VIEWED
tick the explicit confirmation → "Approve & Sign"        ─►  approve bound to the hash shown      APPROVED   DOCTOR_APPROVED
                                                             unsigned PDF built; its hash recorded
                                                             provider gates: enabled+confirmed, level ≥ policy, enrolled
                                                                   SIGNING    SIGNATURE_REQUESTED
                                                             provider returns result (sync, or webhook)
                                                             final PDF validated, SHA-256 recorded, stored (private bucket)
                                                                   SIGNED     SIGNATURE_COMPLETED
                                                             issued, member emailed (no content)       ISSUED     ISSUED
Reject → VOID · Request changes → DRAFT · Revoke → REVOKED · past expiry → EXPIRED
```

### Routes

| Route | Who | Purpose |
|---|---|---|
| `/doctor` | verified practitioner | Overview, Patients, Pending Reviews, Documents, Prescriptions, Profile, Templates, Signature, Audit |
| `/member/documents` | the member | **My documents** (own issued documents: View, Download, Verification link; never regenerate/edit) and **Requests** (ask for a letter or a prescription/order, follow progress, cancel while waiting) |
| `/verify/$token` | anyone (QR target) | document ID, type, issue date, practitioner, "Registration: Verified", status — nothing else |
| `/admin` → **Clinical Docs** | administrator | **Requests** (intake), Doctors, Templates, Documents, Signatures (providers + policy), Audit, Retention |
| `POST /api/public/signatures/webhook` | signature provider | HMAC-authenticated completion callback |
| `POST /api/public/inventory/maintenance` | cron | now also marks overdue issued documents `EXPIRED` |

Server logic is TanStack Start server functions (`src/lib/clinical/*.functions.ts`) over `SECURITY DEFINER` database functions; **no Supabase Edge Function was added** (the existing app keeps server logic in the app's server runtime, and the PDF library runs there).

### Requests (intake)

A **request is not a document.** A member (ID-verified, max 3 open) asks for a letter or a prescription/order; an administrator can also open one on a member's behalf. The administrator assigns it to a verified practitioner (a prescription request only to one authorised to prescribe) — which also records the practitioner-patient assignment — or declines it with a reason. The practitioner starts a draft *from* the request (it links) or declines it; issuing the linked document marks the request FULFILLED, voiding the draft returns it to the practitioner's queue. The member's optional note is visible to the member and assigned practitioner only; administrators never see it. Nothing in this flow writes or suggests a clinical value.

### Data model (migrations `20261002001000_clinical_documents.sql`, `…002000_clinical_template_wording.sql`, `…003000_clinical_document_requests.sql`)

`doctor_profiles`, `doctor_patient_assignments`, `document_templates`, `medical_documents`, `prescription_orders`, `document_signatures`, `document_events` (append-only), `document_verifications` (append-only), `signature_providers`, `document_signature_policy`, `document_counters`, `document_verify_attempts`, `clinical_retention_policy`, `document_requests` · private storage bucket `clinical-documents` (PDF only, 10 MB, no client policy).

Document references: `CP-MED-2026-000184` / `CP-RX-2026-000012`. Verification tokens: 256-bit random (43 URL-safe characters), generated server-side, never sequential.

### Signature providers

`SignatureProvider` (`src/lib/clinical/signature-provider.ts`): `createSigningRequest`, `getSigningStatus`, `downloadSignedDocument`, `verifySignature`, `cancelSigningRequest`. Adapters (`signature-providers.server.ts`):

| Adapter (`provider`) | What it is | Level |
|---|---|---|
| `internal_simple` | Practitioner confirms while signed in; an HMAC binds the unsigned-PDF hash, content hash, practitioner and time. **Not** a cryptographic signature, no certificate. | **SIMPLE** only. Refused for prescriptions. |
| `external_generic` | Provider-neutral REST contract (see file header). A real vendor needs a thin adapter mapping its API to it. **Not yet integrated or tested against any real provider.** | Whatever compliance records — starts at SIMPLE |

The assurance level is **a recorded human decision** (`signature_providers`, `document_signature_policy`: who confirmed, when, on what basis). Nothing is usable until an administrator records it in **/admin → Clinical Docs → Signatures**. Code never claims "advanced" or "qualified".

### Operating it (first-time set-up)

1. Apply the migration. 2. Create the practitioner's profile (**Doctors → Add practitioner**), have a *different* administrator **verify** it against the HPCSA register and (if appropriate) authorise prescribing. 3. Assign patients. 4. Replace the placeholder seed templates with practitioner-approved wording (**Templates**): submit → the practitioner approves in `/doctor → Templates`. Seeds carry a marker that blocks activation. 5. In **Signatures**, record the compliance decision for each document type and enable the confirmed provider. 6. Set the env vars. Only then can a document be created.

### Security and privacy notes

- **Transport/at rest:** TLS and encryption at rest are Supabase platform features (not configured here). Files live only in a private bucket; every open mints a **60-second signed URL after the access is audited**.
- **Authorisation:** every function takes the actor from the verified JWT (`requireSupabaseAuth`); the database re-checks role/ownership. Server functions are Bearer-token calls, not cookie-authenticated, so classic CSRF does not apply; clinical pages are `no-store`, unframeable, `noindex` (`security-headers.ts`).
- **Verification endpoint:** rate limited per hashed requester (30/min) plus a failure limiter (10 unknown-token attempts/15 min). Both are atomic increments: a failure slot is reserved *before* the lookup and refunded only when the token proves to be a real document, so parallel guesses cannot overshoot; fails closed; unknown and malformed tokens are indistinguishable; 256-bit tokens make guessing infeasible. `cf-connecting-ip` is preferred; `x-forwarded-for` is a fallback and can be spoofed if the app is not behind a trusted proxy.
- **Integrity:** the stored PDF is re-hashed on every verification and compared with the hash recorded at signing; a modified file reports "could not be verified". Provider-returned PDFs are structure-checked (header/EOF, parseable, no JavaScript/launch/embedded files, ≤ 10 MB).
- **No health data** in audit metadata (codes and hashes only), logs, analytics, error reports, emails or the public page. Free text (review notes, revocation reasons) stays in access-controlled columns.
- **Not implemented:** malware scanning (Supabase Storage has none built in; files are generated by the server or returned by a provider, never uploaded by users); a purge/retention job (deliberately none — see below); automatic suspension of a practitioner's documents.
- **Retention:** nothing is deleted — `DELETE`/`TRUNCATE` on documents, prescriptions, signatures, events and verifications are blocked by trigger and privilege; revocation is not deletion. Retention periods in `clinical_retention_policy` are **proposals** awaiting confirmation. Note the foreign keys to `auth.users` are `ON DELETE RESTRICT`: a member or practitioner with clinical records cannot be hard-deleted from Auth; a POPIA erasure request needs a legal decision.
